## 1. Facts that drive the decision (verified in the code at the base commit)

1. `app_worker` has no INSERT on `identity.person`, `identity.principal`, `identity.role_assignment`, `identity.role_change_request` or `identity.enrolment_token`. It has SELECT and a few UPDATE grants under audience `system` (2402 lines 124-177, 340-372). The INSERT policies (`person_admin_insert`, `principal_admin_insert`, `role_assignment_admin_insert`, `enrolment_token_admin_insert`) are `TO app_api` and need an `admin_pool` staff session.
2. `identity.guard_enrolment_token` (2401): an insert starts `requested` with no hash; `requested → approved` needs `approved_by_person_id = app.person_id`. CHECK: approver ≠ requester. The principal must be `admin_pool`.
3. `identity.guard_role_change_request` (2401): an insert needs `requester_person_id = app.person_id`; approval needs `approver_person_id = app.person_id` and approver ≠ the subject's person; `approved → applied` is free. `role_assignment.granted_via_request_id` is NOT NULL with a foreign key to `role_change_request`.
4. The API rule (`approveEnrolmentToken`): the approver may be neither the requester nor the subject. **The requester may be the subject.** So the issue's premise "two admins cannot approve each other's tokens" holds only when the requester is one of the two admins. With a requester who is not the approver, a crossed pairing satisfies every rule (section 3).
5. DEVOPS-PLAN 16.2 already fixes the human control: two named custodians, the `gh-bootstrap-<env>` AWS role enabled only by approval-by-apply with two human approvals, a one-off ECS task with a dedicated role that "may only call the bootstrap function", tokens written to per-person Secrets Manager secrets that only the other custodian can read (DPR-10, DPR-23), and "expired token → repeat from step 1". DO-10 (HEAAA-138, DevOps) owns `bootstrap.yml` and `scripts/bootstrap/**`.
6. Graphile `queue.add_job` and `queue_api.enqueue` are executable by `app_worker` and `app_api` only (`harden.sql`). `queue_api.enqueue` does not check `current_user`; it accepts a task type only when `queue_api.task_type.api_enqueue` is true. `identity.admin_event` is job class `job`, so its `api_enqueue` is already true by default (`enqueue.ts` line 55) and `app_api` can already enqueue it. The `audit.event` insert policy accepts function-owner roles under a user audience and `app_worker` under `system` (0203).
7. `audit.event.request_id` is a `uuid`; `job_id` is text ≤ 200; `event_origin` needs one of them, and "request_id is null for worker jobs, which use job_id instead" (0200 lines 55-56, 83-84). `identity.principal.status` is `active`, `suspended` or `disabled`; `role_assignment` is revoked by setting `revoked_at` (0500).
8. The worker's security-notice port defaults to refusing when no mail channel is configured (`apps/worker/src/compose.ts` line 124), so without a configured channel every `identity.admin_event` job retries and dead-letters and no notice is sent.
9. Every identity trigger function (`0501`, `2401`) is invoker rights (no `SECURITY DEFINER`). When it fires inside the definer function it runs as `identity_bootstrap_owner`, so that role needs `USAGE` on `kernel`, `EXECUTE` on `kernel.uuid1`/`kernel.setting` and SELECT on the columns the triggers read (`principal.person_id`, `realm`, `subject`; `role.realm`, `privileged`, `location_bound`). `EXECUTE` on a trigger function is checked only at `CREATE TRIGGER`, never when the trigger fires. `kernel.setting(text)`, `kernel.uuid1(text)`, `kernel.uuids(text)` and `USAGE` on `kernel` are granted to named roles only (0001 lines 9, 31). `organisation.organisation` is `FORCE`d with read policies `TO app_api, app_worker` only (0301). The identity tables have no foreign key to `organisation.organisation`.
10. The API's audit vocabulary for the rows this function writes (`service.ts`): principal creation is one `create` row, `resource_type` `identity.principal`, `change` `{realm}` (person and principal in one row); a role change request is `role_change_request` on `identity.role_change_request` with `change` `{subjectPrincipalId, add, remove, before}`; its approval **and** apply is one `role_change_decision` row with `change` `{decision: "applied", subjectPrincipalId, requesterPersonId, approverPersonId, before, after}`; the `role_assignment` insert has no audit row of its own; token request is `create` on `identity.enrolment_token` with `change` `{principalId}`, token approval is `update` with `change` `{status: "approved"}`. The stored request is `change` = `JSON.stringify({add: sortRefs(add), remove: sortRefs(remove)})`, `before` = `JSON.stringify(sortRefs(before))`, with `RoleRef` = `{roleKey, locationId?}` (the key is omitted when there is no location). `request_hash` = `requestHashOf(subject, add, remove, before)` (lines 56-73). The token is `randomBytes(32).toString('base64url')` (43 characters, no padding); `token_hash` = SHA-256 of that string's UTF-8 bytes (`createHash('sha256').update(token)`, line 374), and the enrolment lookup hashes the presented string the same way (`hashPresentedToken`, `tokens.ts` line 31, shape `^[A-Za-z0-9_-]{43}$`).

## 2. D-1: SECURITY DEFINER function or new `app_worker` INSERT grants

**Question.** How does the bootstrap write rows that `app_worker` may not write?

| Option | For | Against |
| --- | --- | --- |
| A. New `app_worker` INSERT grants and `system` policies on person, principal, role_change_request, role_assignment, enrolment_token | Few objects | Every worker job, for the life of the system, could create admin principals and grant `org_admin`. The "refuses if any admin exists" rule would live only in application code. Breaks the C4 premise that no single compromised tier can mint an admin |
| B. A definer function owned by a new `NOLOGIN` owner role, `EXECUTE` granted to `app_worker` | The latch and the C4 steps are in the database, in one call | A compromised worker could call it in any environment where the bootstrap has not run yet. RK-5 means this window is real: with one human, TC-SEC-11 stays Blocked and staging can stay un-bootstrapped for months |
| **C. A definer function owned by a new `NOLOGIN` owner role, `EXECUTE` granted only to a new dedicated login role `app_bootstrap`** whose database credential only the bootstrap task can read | The latch and the C4 steps are in the database. No running service can call it; reaching it needs the dual-controlled `gh-bootstrap-<env>` role (16.2). Matches 16.2 step 1 ("the job's role may only call the bootstrap function") | One more login role, one more secret, one more owner role |

**Choice: C.** Reason: the first admins are the root of trust of the admin realm. A permanent write path (A) or one reachable from the always-running worker (B) is a standing privilege-escalation route for a once-per-environment action. C costs two roles and one secret, all reversible. It keeps the existing C4 triggers in force (the function sets `app.person_id` per step instead of bypassing them) and follows SHARED-BOUNDARIES 6.2 rule 3: the definer checks its caller itself. Standards: least privilege; C4; SHARED-BOUNDARIES 6.2; DEVOPS-PLAN 16.2 step 1.

Notes on the list:
- **No Setting is read (G-2, F02B-SA-03 (c)).** The token lifetime and the role change request's `expires_at` are constants in the function body: token `expires_at` = `now() + interval '30 minutes'` (the 26.3 value and the `enrolment_token_minutes` default; the API's range is 5-120); request `expires_at` = `now() + interval '30 minutes'`. The request is a deliberate departure from the API's `role_request_hours` (default 24 h): it is approved and applied in the same transaction, so its window is never used, and a short value means a request left behind by a later bug cannot be approved a day later. Reason for constants rather than reading `kernel.setting`: the Setting is writable through T-CONF by one enrolled admin, and reading it would give this role a privilege on `kernel.setting` that it otherwise does not need (same reasoning as the D-1.3 bounds).
- **No `EXECUTE` on trigger functions (F02B-SA-03, imprecision).** Revision 2 listed it; it has no effect when a trigger fires (fact 9) and is dropped.
- Not granted: DELETE anywhere; any right on `identity.session`, `elevation_grant`, `webauthn_challenge`, `person_link_request`, `staff_profile`; any `admin_credential` column other than G-11; any `queue` schema right; any `kernel` table.
- `queue_api.enqueue` has no `current_user` restriction; the gate is `task_type.api_enqueue` (fact 6). `identity.admin_event` already has `api_enqueue = true`, so this caller needs no registry change, and `app_api` gains no new reach. The grant lets the owner role enqueue any `api_enqueue` type, but the only code that runs as this role is the function body, which enqueues `identity.admin_event` only; test 1 checks the jobs it leaves.
- Outside this role: `identity.bootstrap_run` gets SELECT for `app_worker` (policy under audience `system` and organisation; the run-level notice reads it, section 3 step 4) and for `app_api` (T-CONF(admin) read).

**New table `identity.bootstrap_run`** (C1, insert-only, RLS forced): `id`, `organisation_id`, `run_ref` (CI run ID, text ≤ 100), `ticket_ref` (text ≤ 100), `mode` (`create` | `reissue`), `principal_ids uuid[]` (the two bootstrap principals), `custodian_person_ids uuid[]`, `custodian_idp_ids text[]` (each custodian's IAM Identity Center user ID, from the approved record; 2 values, each ≤ 200, F02B-SEC-05), `token_expires_at`, `created_at`. Constraints (ARCHITECTURE 22.4 row, revision 3): the three arrays have exactly 2 elements; UQ (`organisation_id`) WHERE `mode = 'create'`, so the database itself holds the "exactly one create run" of D-1.3 item 1; index (`organisation_id`, `created_at`); `kernel.append_only`. SELECT for `app_api` under the admin realm's T-CONF read (it is evidence for the privileged-access review). No UPDATE or DELETE grant to anyone. It is how a re-run recognises the two bootstrap principals (D-1.3).

**Function** `identity.bootstrap_admins(p_run_ref text, p_ticket_ref text, p_enrollees jsonb, p_custodians jsonb, p_token_hashes bytea[]) RETURNS jsonb`, `SECURITY DEFINER`, `SET search_path = pg_catalog`, schema-qualified names only, owner `identity_bootstrap_owner`, `REVOKE ALL FROM PUBLIC`, `GRANT EXECUTE TO app_bootstrap`.
- `p_enrollees`: two objects `{handle, display_name}`. Handles follow the existing `admin_pool` subject rule and are distinct.
- `p_custodians`: two objects. Each is either `{display_name, idp_id}` (a custodian who is not an enrollee) or `{enrollee: 1|2, idp_id}` (a custodian who is that enrollee). `idp_id` is required and the two differ. Custodian `i` retrieves the token of enrollee `i` (D-2). Refused if custodian `i` is enrollee `i`, or if the two custodians are the same.
- `p_token_hashes`: two SHA-256 values (32 bytes each, distinct), hash `i` for enrollee `i`. The function never sees a plain token.

**Caller binding (6.2 rule 3).** First statements: refuse unless `session_user = 'app_bootstrap'`, `app.org_id` is set, and the organisation exists (read through G-3; else `bad_input`). Then set, transaction-local, `app.audience = 'system'` and `app.job_scope = 'org'`. Before returning, restore `app.person_id`, `app.audience` and `app.job_scope` to the values they had on entry (F02B-SEC-06a); on an exception the transaction rolls back and the caller's command exits.

**Concurrency.** `pg_advisory_xact_lock` on `identity.bootstrap_admins:<org_id>` before the latch read, so two runs serialise and the second sees the first's rows.

**D-1.3 Latch and modes (refines ARCHITECTURE 26.3 "refuses if any `admin_pool` principal exists").**
- **create**: no `admin_pool` principal exists in the organisation, in any status. Creates everything in section 3.
- **reissue**: all of the following hold, else refuse.
  1. **Run history (F02B-SA-01).** Exactly one `bootstrap_run` with mode `create` exists in the organisation (the first run), **and** every `bootstrap_run` with mode `reissue` has `principal_ids` equal to that first run's `principal_ids` (as sets). Any number of reissue rows may exist for this item; their count is bounded by item 3 only. The only `admin_pool` principals in the organisation, in any status, are the first run's two `principal_ids`, and the handles given equal theirs (each new reissue row records the same `principal_ids`, so the invariant holds for the next run).
  2. **Age bound:** `now() < ` the first run's `created_at + interval '7 days'` (F02B-SEC-01).
  3. **Count cap:** fewer than **2** `bootstrap_run` rows with mode `reissue` exist (so at most two reissues, three runs in all) (F02B-SEC-01).
  4. The targets are the bootstrap principals that have **never** had an `admin_credential` row (revoked rows count); there is at least one.
  5. **Each target** has status `active` (not `suspended` or `disabled`, so a kill-switched principal is never revived; this is also the API's `requestEnrolmentToken` condition, and enrolment fails for a principal that is not active; F02B-SEC-02, F02B-SA-07 (a)) **and** holds an unrevoked `role_assignment` of `org_admin` whose `granted_via_request_id` is the request created for it by the first run (F02B-SEC-02). If any target fails this, the whole call refuses (`target_state`); it does not skip that target.
  For each target only: open tokens (`requested` or `approved`) are set `expired` (audited, step 3), and one new token is created as in section 3 with the new run's custodians. A principal that has a credential gets nothing (it is **skipped**, and the result says so, section 3 step 5). Roles are not touched. A new `bootstrap_run` row records the run with the first run's `principal_ids` (item 1).
  Known limit (F02B-SA-07 (b)): item 1 closes reissue as soon as any other `admin_pool` principal exists. Once one bootstrap admin has enrolled, that admin alone can create such a principal (`principal_admin_insert` needs only an admin session), which closes reissue for the other, unenrolled bootstrap principal; section 6 states the limit and the runbook step.
  The two bounds are **constants in the function body**, not Settings. Reason (deviation from the reviewer's "value from Setting"): `kernel.setting` is writable through the admin realm's T-CONF path, so once one bootstrap admin has enrolled, that single admin could widen the window, which is the single-person mint C4 forbids. Changing a constant needs a reviewed migration. Outside the bounds, recovery is the normal P-4 path (two enrolled admins), or, if fewer than two admins are enrolled, a reviewed data-repair change under 21.7 with its own dual approval; this function stays closed.
- **refuse** in every other case, with `PS001` and the message `bootstrap refused`, and no write. This includes: any other `admin_pool` principal; both bootstrap principals have a credential; mismatched handles; a target that is not `active` or lost its `org_admin` assignment; the age bound passed; the reissue cap reached; a missing `org_admin` role (reference data not applied). The reason is returned only as a fixed code in the error detail (`latch_closed`, `reissue_expired`, `reissue_cap`, `target_state`, `bad_input`, `reference_data`), never with row data.

Reason for reissue: 16.2 step 7 says an expired token is fixed by repeating the run. Under the literal 26.3 rule the first run's principals would close the latch, so one missed 30-minute window would leave an environment with no admin and no repair path short of superuser surgery. Reissue is bounded: it needs the same dual-controlled pipeline, cannot create a new principal, cannot touch an enrolled, suspended, disabled or de-roled principal, and closes forever once both have enrolled a key, after two reissues, or seven days after the first run, whichever comes first. It also covers the case where one enrollee enrolled and the other did not; one admin alone cannot issue a token (C4).

## 3. D-2: who requests and who approves the first two tokens and role grants

**Question.** Each token and each role grant needs a requester and an approver who are persons (`identity.person`), with approver ≠ requester and approver ≠ subject.

| Option | Against |
| --- | --- |
| A. Each enrollee approves the other's token | The enrollees did not act; the audit would name approvers who approved nothing. Fails when the enrollees are the custodians (requester and approver collide) |
| B. A synthetic "system" person requests and approves | A system person cannot be both (CHECK). Two synthetic persons hide the humans who actually approved, against TC-SEC-11 ("both people recorded in the audit") |
| **C. The two custodians, crossed** | — |

**Choice: C.** For enrollee `i`, with custodian `i` the one who will read that token (16.2 step 3) and custodian `j` the other:

| Row | Requester | Approver |
| --- | --- | --- |
| `role_change_request` granting `org_admin` (no location) to enrollee `i` | custodian `j` | custodian `i` |
| `enrolment_token` for enrollee `i` | custodian `j` | custodian `i` |

This follows ARCHITECTURE 26.3 ("shown once to the approver, who hands it over out of band") and DPR-23. Every rule holds in all cases: the approver is never the requester (`i ≠ j`); the approver is never the subject (custodian `i` ≠ enrollee `i` is refused at input). When the custodians are the enrollees (16.2 allows it, crossed), custodian `i` is enrollee `j`: the approver of enrollee `i`'s rows is enrollee `j` and the requester is enrollee `i` itself. The requester may be the subject (API rule, fact 4), and the approver is neither. Each custodian appears once as requester and once as approver, which mirrors the two human approvals of the approval-by-apply change. A custodian who is not an enrollee is created as a `person` with no principal (cannot sign in). A custodian who is an enrollee reuses the enrollee's person.

**Steps inside the one call (create mode), triggers enforced throughout:**
0. Insert the `bootstrap_run` row first (its `id` is the run ID used below).
1. Insert the enrollee persons, any non-enrollee custodian persons, and two `admin_pool` principals (`subject` = handle, status `active`). `created_by_job` = the `bootstrap_run.id`.
2. Per enrollee `i`: set `app.person_id` = custodian `j`; insert the role change request and the enrolment token (`requested`, `expires_at` = `now() + interval '30 minutes'`, section 2.1 notes). Set `app.person_id` = custodian `i`; approve the request (`approved`, `approver_person_id`, `decided_at`); insert the `role_assignment` (`org_admin`, no location, `granted_via_request_id` = the request); set the request `applied`; approve the token with hash `i` (`token_hash`, `approved_by_person_id`, `expires_at` = `now() + interval '30 minutes'`, `approved`).
   **Stored shapes and hashes, exactly as the API writes them (F02B-SA-04; fact 10).** With `S` = the enrollee's principal ID as lower-case hyphenated text (`uuid::text`):
   - `change` = the JSON text `{"add":[{"roleKey":"org_admin"}],"remove":[]}` (no `locationId` key, because the role is not location-bound); `before` = `[]`.
   - `request_hash` = SHA-256 of the UTF-8 bytes of exactly `{"subject":"S","add":[["org_admin",null]],"remove":[],"before":[]}`, which is the canonical form of `requestHashOf(S, [{roleKey: "org_admin"}], [], [])`. The function builds this string by text concatenation (`convert_to(…, 'UTF8')` then `sha256`), not through `jsonb` output, whose spacing differs.
   - `token_hash` = `p_token_hashes[i]`, which the command computes as SHA-256 of the **UTF-8 bytes of the 43-character base64url string** (`createHash('sha256').update(token)`), not of the 32 raw random bytes. It is the value `hashPresentedToken` derives at enrolment, so `enrolment_token_lookup` matches it. The function checks each hash is 32 bytes and the two differ.
   Test 7 compares both values with the TypeScript helpers.
3. **Audit rows (F02B-SA-02).** The function writes exactly the rows the API writes for the same changes (fact 10), plus the two the API has no equivalent for:

   | Write | `action` | `resource_type` | `resource_id` | `actor_person_id` | `change` (besides the marker below) |
   | --- | --- | --- | --- | --- | --- |
   | `bootstrap_run` insert | `create` | `identity.bootstrap_run` | run ID | null | `{mode, principalIds}` |
   | non-enrollee custodian person insert (no API equivalent) | `create` | `identity.person` | person ID | null | `{}` |
   | enrollee person + principal insert | `create` | `identity.principal` | principal ID | null | `{realm: "admin_pool"}` (as the API) |
   | role change request insert | `role_change_request` | `identity.role_change_request` | request ID | custodian `j` | `{subjectPrincipalId, add: [{roleKey: "org_admin"}], remove: [], before: []}` |
   | request approval, `role_assignment` insert and apply (one row, as the API) | `role_change_decision` | `identity.role_change_request` | request ID | custodian `i` | `{decision: "applied", subjectPrincipalId, requesterPersonId, approverPersonId, before: [], after: [{roleKey: "org_admin"}]}` |
   | token insert | `create` | `identity.enrolment_token` | token ID | custodian `j` | `{principalId}` |
   | token approval | `update` | `identity.enrolment_token` | token ID | custodian `i` | `{status: "approved"}` |
   | reissue: open token set `expired` (no API equivalent; F02B-SEC-04.2) | `update` | `identity.enrolment_token` | token ID | null | `{status: "expired", reason: "bootstrap_reissue"}` |

   Every row: `organisation_id` = `app.org_id`; `realm` = `worker`; `audience` = `system`; `outcome` = `allowed`; **`job_id` = `bootstrap-admins:<p_run_ref>`** (text; `p_run_ref` ≤ 100 characters, so ≤ 117); **`request_id` = null** (the 0200 rule for worker rows; revisions 1 and 2 put a value there, which was wrong in revision 1 by type and in revision 2 by meaning); `reason` = `p_ticket_ref`; `actor_principal_id` = the custodian's principal only when that custodian is an enrollee, else null; and `change` also carries the pipeline marker `{"via": "bootstrap_admins", "bootstrapRunId": …, "mode": …}` (F02B-SEC-05). So the audit says "the pipeline, for custodian X", the role grants appear under `role_change_request`/`role_change_decision` where the audit viewer and the privileged-access review look for role changes, and `bootstrap_run.custodian_idp_ids` ties X to a real Identity Center account and to the two approvals of the approval-by-apply record. The `job_id` prefix is the one `event_insert_bootstrap` requires (G-13). No separate row for the `role_assignment` insert (the API writes none; the decision row's `after` records it).
4. Enqueue `identity.admin_event` for each enrollee: `enrolment_token_requested`, `enrolment_token_approved`, `role_change_decided`, with job keys `<kind>:<row id>`, **and one run-level event** `bootstrap_run` (new kind, added to `ADMIN_EVENT_KINDS` in both the API and worker lists, which a test keeps equal) with job key `bootstrap_run:<run id>` (F02B-SEC-04.3). The existing handler (HEAAA-412) raises the compliance alert and the PHI-free notice to the security contact (B2-9) for each. For `bootstrap_run` the handler reads the `bootstrap_run` row and sends one notice holding mode, run ID, `run_ref`, `ticket_ref`, token expiry and the principal IDs (no names, no handles, no token data), and raises a `privileged_change` alert of severity `high`; it writes no audit row (the function did). With no compliance officer assigned yet, the notice to the security contact mailbox is the detection layer; the alert has no recipient until a compliance role is granted. That mailbox is therefore a precondition of the run (section 4 step 1a).
   **Reissue mode** (F02B-SEC-04.2): each open token set `expired` gets the `update` row of the step 3 table; each new token gets the `enrolment_token_requested` and `enrolment_token_approved` events and its audit rows as in step 3; and the run-level `bootstrap_run` event is sent with mode `reissue`. No `role_change_decided` event (roles are not touched).
5. Restore the three settings (section 2.1). Return `{mode, run_id, expires_at, enrollees: [{slot: 1|2, principal_id, result: "issued" | "skipped", token_id | null}, …]}` with **one entry per enrollee slot**, in slot order (F02B-SA-06 (b)). In create mode both are `issued`. In reissue mode an enrollee that already had a credential is `skipped` with `token_id` null. No hash and no token in the return value.

The bootstrapped admins hold `org_admin` only. Every later role, including `compliance_officer`, goes through C4 in the app. Elevation then works as for any admin (two keys, 26.3 B2-8).

## 4. D-3: how the plain tokens reach the custodians without entering logs or artifacts

**Choice:** DEVOPS-PLAN 16.2 step 3 as written, with the process contract below. No alternative was needed; the open point was only where the plain token is created and in what order.

**The run-once command** (`apps/worker`, entry `bootstrap-admins`, same release image; runs as a one-off ECS task under the `gh-bootstrap-<env>` path; not a queue job and never registered in the worker's job registry or crontab):
1. Reads its inputs (enrollee handles and display names, custodian entries with their IAM Identity Center user IDs and role ARNs, enrollee identity ARNs for the explicit deny, ticket reference, and the security-contact check of 1a) **from the approved record `/approved/bootstrap-<env>`**, not from workflow inputs. The agent identity cannot write that record (DEVOPS-PLAN 7.4), so it cannot redirect a token to itself. The run reference is the CI run ID.
   1a. **Security-contact precondition (F02B-SEC-04.1).** The command refuses, before any secret or database call, unless (i) the environment configuration it shares with the worker names a security-notice channel (the same value whose absence makes the worker's notice port refuse, fact 8), and (ii) the approved record carries `security_contact_verified_at` no older than 72 hours and `security_contact_test_ref`. Those two fields are written by the custodians after runbook step 0 (DO-10): a test notice sent through the deployed worker's notice channel and confirmed received by the mailbox owner. Until OPEN-6 names that owner, no environment can satisfy this, which adds to RK-5 rather than weakening the check.
2. Generates two tokens in memory: `randomBytes(32).toString('base64url')`, the same format the API's approve path uses (`service.ts` line 372); computes each `token_hash` as SHA-256 of the token **string's UTF-8 bytes** (section 3 step 2; it reuses the API's `sha256` helper from `apps/api/src/modules/identity/tokens.ts` through a shared package export, or an identical one-line helper covered by test 7).
3. **Before the database call**, creates the two secrets `bootstrap/<env>/token/<slot-i>`, each encrypted with custodian slot `i`'s customer-managed key (section 4.1 item 3). If this fails, it stops; nothing is in the database. **Access to each secret (F02B-SA-06 (a)), by action:**
   - **Read** (`secretsmanager:GetSecretValue`, and `kms:Decrypt` with that slot key): allowed only to custodian `i`'s Identity Center role. Denied to everyone else, explicitly including enrollee `i`'s identity and the bootstrap task role. The read control is the slot key's policy (the task cannot change it) plus explicit denies in the task role's identity policy.
   - **Modify** (`PutSecretValue`, `UpdateSecret`, `RestoreSecret`, `RotateSecret`, `ReplicateSecretToRegions`, `PutResourcePolicy`, `DeleteResourcePolicy`; `kms:PutKeyPolicy`, `kms:CreateGrant` on the slot keys): denied to every principal after creation, including the bootstrap task role and the custodians. Tag actions are not in this list: `CreateSecret` with the required `run_ref` tag needs `secretsmanager:TagResource`, and a tag holds no secret.
   - **Delete** (`DeleteSecret` with `ForceDeleteWithoutRecovery`): **allowed** to the bootstrap task role (deletion on failure in step 4, of skipped secrets in step 4a, and at expiry in step 6) and to the platform-admin break-glass role (cleanup when the task cannot, step 4); denied to every other principal. No deny statement may cover `DeleteSecret` for these two roles; test 8 and the TC-SEC-11 rehearsal check that both deletions succeed.
4. Calls `identity.bootstrap_admins` in one transaction as `app_bootstrap`. If the call fails or is refused, it force-deletes both secrets and exits non-zero. So a committed bootstrap always has its secrets. If the secret deletion itself fails, it exits non-zero naming the secret ARNs, and the runbook deletes them with the break-glass role.
   4a. **Skipped enrollees (F02B-SA-06 (b)).** After a successful call, for every enrollee whose result is `skipped` (section 3 step 5), the command force-deletes that slot's secret **at once**, before it writes any output, and checks it is gone. The secret holds a token whose hash was never stored, so no custodian ever sees it. If that deletion fails, the command exits non-zero naming the ARN and the slot as `skipped`, and the runbook deletes it before the custodians are told to read anything.
5. Overwrites the token buffers. Writes to stdout only: mode, run ID, expiry, and per enrollee slot: principal ID, `issued` or `skipped`, token ID and secret ARN (issued), or "deleted" (skipped). The workflow keeps that result as evidence. The logger is created with no token in scope; a unit test asserts that no output line contains either token or its hash.
6. `bootstrap.yml` (DO-10) ends with a step that waits until the returned expiry and force-deletes the remaining secrets, then checks they are gone. The secret is deleted at expiry, not on use (DEVOPS-PLAN 16.2 step 3 as amended at `d4c0bf3`): the token is useless after use (status `used`) and after expiry, so deletion at expiry bounds the secret's life to 30 minutes either way. CloudTrail alerts on every `GetSecretValue` (16.2).

The token never enters the database (only its hash), the workflow log, a CI artifact, a task comment or a chat. The custodian reads it with MFA through their own Identity Center role and hands it over in person or through a secure channel of their choice (16.2). After the run, both custodians confirm the run-level notice (section 3 step 4) reached the security contact; a missing notice is handled as a security incident (the run itself is not undone).

### 4.1 `app_bootstrap` credential and bootstrap task hardening (normative for DO-10; F02B-SEC-03)

The function cannot see dual control; it trusts whoever logs in as `app_bootstrap`. So the credential and the task that holds it carry the control:

1. **Credential lifecycle.** The secret `<env>/db/app-bootstrap` has a resource policy that is deny-by-default; the allow for the bootstrap task role exists only while an unexpired approval-by-apply record for `bootstrap-<env>` exists (16.2), applied and removed by that record. The password is rotated after every run (final workflow step, success or failure) by Secrets Manager managed rotation, so no human, agent or log ever holds a usable value between runs. `app_bootstrap` has `CONNECTION LIMIT 1`. A page fires on any `GetSecretValue` of that secret outside an approved window.
2. **Task pinning, as the migration task (DEVOPS-PLAN 7.5, DPR-28 and 28-a).** The bootstrap task definition has a fixed `entryPoint`: the same statically linked launcher, which refuses any argv and any environment variable outside a whitelist (excluding `NODE_*`, `LD_*` and similar) and execs the `bootstrap-admins` command with an environment it builds. The command takes no arguments. `iam:PassRole` for the bootstrap task role and its execution role is limited to that task definition family and to the `gh-bootstrap-<env>` role. A security page fires on every `RunTask` of that family whose CloudTrail `requestParameters.overrides` is non-empty, and on any `RunTask` outside an approved window. `enableExecuteCommand` is false and `ecs:ExecuteCommand` is denied on the cluster for that family.
3. **Token-secret rights of the task role.** On `bootstrap/<env>/token/*` only: `secretsmanager:CreateSecret` (condition: `secretsmanager:KmsKeyId` equals the slot key for that name; tag `run_ref` required) and `secretsmanager:DeleteSecret` (force, no recovery window); `kms:GenerateDataKey` and `kms:Encrypt` on the two slot keys. Explicitly **denied** (identity policy and key policy): the read and modify actions of section 4 step 3 (`secretsmanager:GetSecretValue`, `PutSecretValue`, `UpdateSecret`, `RestoreSecret`, `RotateSecret`, `ReplicateSecretToRegions`, `PutResourcePolicy`, `DeleteResourcePolicy`, and `kms:Decrypt` / `kms:PutKeyPolicy` / `kms:CreateGrant` on the slot keys). `DeleteSecret` is **not** denied to this role or to the platform-admin break-glass role (section 4 step 3, F02B-SA-06 (a)). The two slot keys and their policies are created by the approved apply, not by the task; the key policies do not delegate to the account root for `kms:Decrypt`, so an IAM policy elsewhere in the account cannot grant reading. Read-back is impossible for the task, so a tampered command could at most leak the tokens it generated itself through its own output, which item 2 prevents by pinning the code that runs.
4. AWS behaviour in items 1-3 (rotation, condition keys, override detection, root-less key policies) is design from documentation and **unverified**; DO-10 proves each in staging before the first real run (with TC-SEC-11).

## 6. Risks and limits

- **RK-5.** With one human there are not two custodians, so no environment can run this for real (DEVOPS-PLAN 16 item 2, TC-SEC-11 Blocked). The code and the tests can be built and reviewed; the rehearsal stays Blocked. This decision does not weaken that.
- A database superuser can still create admins directly. That is outside the application's trust boundary (21.2) and is visible in the audit gap and CloudTrail.
- Reissue adds a state the original 26.3 sentence did not name. It is narrower than the alternative (manual database repair) and bounded by 7 days and 2 reissues.
- **Single-admin limit (F02B-SA-07 (b)).** Once one bootstrap admin has enrolled a key, that admin alone can create another `admin_pool` principal (`principal_admin_insert` needs only an admin session). That closes reissue (D-1.3 item 1), and the other, unenrolled bootstrap principal can then never get a token: one admin cannot satisfy C4 to issue it one in the app. The environment is left with a single admin. This decision keeps the latch strict rather than excluding later principals from it, because a latch that ignores principals created after the bootstrap would let a single enrolled admin keep the reissue path open for principals of their choosing. **Runbook step (to be added to DEVOPS-PLAN 16.2 between steps 4 and 6, section 5 row "DEVOPS-PLAN 16.2 amendment" item (iii)):** both enrollees complete enrolment (both keys) before any other admin principal is created or any other admin provisioning is done; the first admin does nothing in the admin realm except register their second key until the second enrollee has enrolled. If the limit is hit anyway, recovery is a reviewed data-repair change under 21.7 with its own dual approval, as for the expired-window case of D-1.3.
- `app_owner` (the migration role) can `SET ROLE identity_bootstrap_owner`, as it can for the other four function-owner roles (21.2 point 1). Residual, no new exposure: migrations are reviewed and run through the pinned migration task.
- `TEMPORARY` on the database is granted to `PUBLIC` by default and so is available to `app_bootstrap`; with no other privilege it reaches nothing. Accepted.
- The custodian accounts in `custodian_idp_ids` come from the approved record; the database cannot verify them. The approval-by-apply record and CloudTrail are the evidence that ties them to the two human approvals.
- Reversible: the roles, function, table and grants are additive and can be dropped by a contract migration.

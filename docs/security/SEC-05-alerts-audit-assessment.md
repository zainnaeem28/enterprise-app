## 2. What holds (verified by reading)

1. **Append-only is enforced three ways.** No UPDATE/DELETE/TRUNCATE grant on `audit.event` or `audit.anchor`; row triggers `refuse_change` (cloned to partitions) and statement triggers on every partition (TRUNCATE); `app_owner` has every privilege revoked on parent and partitions, so a TC-AU-04 step 3 attempt is a `42501` before any trigger. `FORCE ROW LEVEL SECURITY` on all five tables; no policy matches `anonymous` or `public`.
2. **Audit inserts are bounded (SAR-10).** `require_bounded_tx` checks the *setting* (1 to 60 s); `app_api`, `app_worker` and `audit_archiver` carry a role-level `transaction_timeout = 60s`. `occurred_at` is the database clock, not caller input (the module's `INSERT_SQL` omits it).
3. **Actor and scope come from the transaction, not the caller.** `buildRow` takes org, realm, audience, principal and person from `tx.scope`. Free text is limited to `reason` (500), `user_agent` (512) and `change` (16 KB, depth 6, secret-like keys refused unless `*VersionId`). `denied` cannot be recorded as an allowed action.
4. **Fail closed.** `record` runs in the caller's transaction, so a failed audit insert rolls the business change back. `recordDenied` uses a new transaction, never throws, and the caller still gets the denial.
5. **Anchor arithmetic is sound.** Leaf = `sha256(0x00 || row_digest)`, node = `sha256(0x01 || l || r)` (domain separated); the digest covers every column except `anchor_id`; anchor hash chains `prev_hash`, both ranges, count and root; one writer per organisation by advisory lock; a late row is counted and shows as a mismatch; verification recomputes the **full** chain by default (BR-BE01-02 closed), including `chain_link`, `chain_gap`, `row_count`, `root`, `hash`.
6. **BTG database rules.** Insert only for oneself (`holder_principal_id`, person and realm equal the session, `pending`, not revoked); grant keeps holder, patient, reason and times (trigger); `pending` to `justified|not_justified` once; no delete; `btg_review` insert-only with the trigger refusing reviewer = holder (`audit.self_review`) and a grant that is not visible. The service additionally refuses the holder first (`SelfReviewError`) and `FOR UPDATE` locks the grant. `openBtg` writes grant, `btg_open` audit row (reason required) and the event in one transaction. BE-24 makes the review elevation-gated and audits a self-review as a denial.
7. **Export is bounded.** Time range required (CHECK), size limit by setting with a counted `LIMIT max+1`, `export` audit row with reason in the request transaction, chunked and resumable, step 3 re-reads the job `FOR UPDATE` so an overlapping retry adds nothing, one summary event on completion. BE-24 download is requester-only, `ready`, 300 s signed URL, audited in the same transaction, fails closed (503) without the signer.
8. **Alert integrity in the database.** Content columns immutable, forward-only status, closed is final, ack is final, level only up, targets only added, `escalate_at` only while open; patient rule CHECK (admin-realm types never carry a patient); staff INSERT only `red_flag`, realm `google`, creator = self; staff UPDATE only to `acknowledged` by self; every compliance/operations type is writable only under `app_worker` system scope, so no request can forge one. Column-level grants limit what each role can write.
9. **Acknowledge.** Row locked; second ack is a 200 with `alreadyAcknowledged`; one `acknowledged` event by a partial unique index; closed is 409; non-target or invisible is 404 (no existence oracle); `Idempotency-Key` required; audit row has the patient ID but no PHI in `change`.
10. **Escalation job.** Re-reads under lock; no-op when closed, acknowledged, already escalated or `escalate_at` null; early run reschedules; level must be exactly one above; one `escalated` event by index; patients scope when the payload carries a patient, org scope otherwise. The worker port is wired in `worker-ports.ts`.
11. **Stream authorization model.** `NOTIFY` carries IDs only and is **never trusted**: each local principal re-reads the alert under its own scope and RLS, so a forged or stray notification can at worst cause a re-read or a close. Event data is a closed field list (`serialize.ts`, ST-2, schema test); SSE framing uses `JSON.stringify` and a numeric `id:`; `Last-Event-ID` is regex-validated; 3 streams per session and 10 per principal, oldest evicted; a client over 64 KB is destroyed; 15 s ping; session row re-read every 60 s (jittered, passive, never extends the session); `session_revoked` closes at once; ST-3 fault injection test (LISTEN backend terminated) exists in `alerts.dbtest.ts`; reconnect with catch-up after a LISTEN outage.
12. **Serialization and headers.** Stream and alert responses are `no-store`; no PHI or free text in any event.

### SEC05-F01 · High · `audit.anchor` and `audit.verify_anchors` are never scheduled, so tamper evidence does not run
- **Where:** `apps/worker/src/job-registry.ts:40` `WORKER_CRONTAB = toCrontabText([PRIVACY_CRONTAB, REPORTING_CRONTAB])`; `apps/worker/src/m4-registration.test.ts:61-70` asserts the crontab is **exactly** `privacy/expire_packages` and `reporting/refresh_ops`. `AUDIT_CRONTAB` (`jobs/audit/jobs.ts:33`) is exported and imported nowhere; the audit README says "the F-05 runner does not pass a crontab yet (integration step)". The same applies to `INTEGRATION_CORE_CRONTAB` (INT-N9, not assessed here).
- **Issue:** The handlers exist and are registered, but nothing fires them. No anchor is ever written, so the daily check has nothing to recompute and can never raise `audit.anchor_mismatch`. The test pins the omission as expected behaviour, so it will not be noticed.
- **Failure scenario:** An insider with owner-level database access changes or deletes audit rows for a patient lookup. Nothing detects it, ever. TC-AU-08 ("mismatch detected, alert raised") cannot pass on an integrated candidate; the claim in ARCHITECTURE 6 and threat 06 is false in the running system. No application error appears, because a missing schedule is silent.
- **Remediation:** Add `AUDIT_CRONTAB` to `WORKER_CRONTAB` (and update the pinned test to require both audit entries with a handler each). Add a liveness check: an alert or health signal when the newest anchor is older than, say, 10 minutes (DevOps plan lists "anchor job late" as a page; the signal must exist in the product, not only in a dashboard). QA runs TC-AU-08 on the integrated candidate.
- **Owner / parent:** Integrator (worker composition) with Backend Engineer (audit lane); DevOps for the late-anchor signal. Parent HEAAA-25. Blocks acceptance of RA-R1-12.

### SEC05-F02 · High · Anchors are never copied to the object-locked archive; the database owner can rewrite events and the whole chain
- **Where:** `audit.anchor.archived_at/archive_key` are never written (`grep` finds no writer); the export `sink` defaults to `refusingPort('audit_export_sink')` (`worker/src/compose.ts:~212`); the audit README "Not built: object-store sink for exports and anchors". No ticket in TICKETS.md builds the worker step: DO-02 builds the bucket, DO-10 the dual-controlled partition archive and bootstrap.
- **Issue:** ARCHITECTURE 6 says "Each anchor is written to the database **and** to the object-locked archive in the separate log-archive account" and threat 06 relies on it. Today anchors live only in the database whose events they protect. The hash is unkeyed SHA-256, so anyone who can disable the append-only triggers (`app_owner` owns the objects; `rds_superuser`) can alter an event, recompute the Merkle root, and write consistent replacement anchors. This is the SR-BE01-02 finding (rated Low there because DO-09b "covers the workflow"); it is not covered: DO-10 archives partitions, not anchors. It also blocks O-2 (ARCHITECTURE 25.9, O2-4: an admin credential counts only if its enrolment event is in an *archived* anchor), so SEC02-F04 cannot be closed without it.
- **Failure scenario:** As above, with the extra step of rewriting `audit.anchor`; the daily check (once F01 is fixed) passes.
- **Remediation:** Worker step after each anchor (or hourly batch): put `{id, from, to, row_count, merkle_root, prev_hash, hash}` to the Object Lock compliance-mode bucket through a write-only cross-account role, then set `archived_at`/`archive_key` (this needs a defined, single-column worker UPDATE grant on `audit.anchor` or a separate append-only `anchor_archive_receipt` table: an Architect choice, since `audit.anchor` is deliberately immutable). Verification compares the archive copy with the database copy. Test: change a row and rewrite the anchor chain in the database; verification reports the difference against the archive. Until built, record the risk acceptance: "tamper evidence holds only against actors without owner-level database access".
- **Owner / parent:** Architect (receipt design), Backend Engineer (audit lane), DevOps (role and bucket policy, DO-02). Parent HEAAA-25. Blocks RA-R1-12 acceptance and SEC02-F04.

### SEC05-F03 · High · The compliance alerts (BTG, anchor mismatch, kill switch, privileged change) have no producer, and compliance officers cannot reach them
- **Where:** (a) `grep` over `apps` finds the events `audit.btg_opened` (published in `audit/service.ts:154`), `audit.anchor_mismatch` (`verify.ts:105`) and `identity.kill_switch_used` only on the **publish** side. `JobRegistry.registerHandler` is called for `notifications.alert_unacknowledged`, `scheduling.*`, `messaging`, `telehealth`, `calendar_sync` and nothing else; kernel `publish` creates "one job per handler registered", so an event with no handler creates no job and **raises no error**. No code calls `AlertService.raise` with type `btg_opened`, `audit_anchor_mismatch`, `kill_switch_used`, `privileged_change`, `scope_drift` or `integration_down` (callers raise only `red_flag` and `note_unsigned`). (b) `composition.ts:261` builds `new AlertService({ queue, audit })` with **no resolver**, so the `compliance_permission` and `role_location` target kinds throw `422 targets`. (c) ALR-N6: the guard defaults every non-`/admin` path to realm `google`, so an `admin_pool` compliance session gets 403 on `/alerts`, `/alerts/open-ids`, `/alerts/{id}/acknowledge` and the stream, although ARCHITECTURE 32.2 point 1 requires both realms.
- **Issue:** The detective control for BTG (BR-14: "the compliance officer is told at once"), for audit tampering (TC-AU-08), for the kill switch (TC-SEC-13 "alert goes to compliance") and for privileged changes does not exist in the integrated code. Even if a producer is added, the intended recipients cannot read, acknowledge or stream the alert.
- **Failure scenario:** A clinician opens BTG on a colleague's or a public figure's chart (once the route exists, F05). The grant, the audit row and a published event are written; no alert is created; nobody is told; the review queue is the only trace and it has no ageing. Same for a tampered audit row or a killed admin.
- **Remediation:** One owner builds and tests: handlers registered for the three events that call `raise` under system scope with `target_kind = compliance_permission` (permission `audit.btg.review` for BTG and anchor mismatch; the kill-switch and privileged-change recipients per 25.5), IDs-only payloads, `patient_id` null; a real `TargetResolver` wired in the composition (active principals of realm `admin_pool` holding the permission, excluding the actor); fix the realm check so `/alerts*` accepts `google` **and** `admin_pool` (route declaration or guard rule, with a negative test that other realms and patient sessions are refused). Acceptance: dbtests per type showing alert row, `created` event and stream delivery to a compliance session; a publish with no handler fails a test (add a registry check "every published event has at least one handler" to the worker registration test).
- **Owner / parent:** Orchestrator assigns (Backend Engineer, notifications lane; Integrator for composition; Backend Engineer, identity lane for the realm rule). Parent HEAAA-25. Blocks RA-R1-11 and RA-R1-12 acceptance.

### SEC05-F04 · High · `staff_scope_allows_patient` is still the fail-closed stub: red-flag alerts are invisible to every staff session
- **Where:** `db/migrations/1201_staff_alert_rls_and_grants.sql:12` `SELECT false`; `grep` finds no later definition in `db/migrations` (the table `patient.staff_scope` exists since 0700 and the patient policies read it, `0702:53`). The only `CREATE OR REPLACE` is inside `alerts.dbtest.ts`, `clinical/frontdoor/testkit.ts:295` and `clinical/notes/testkit.ts:340`. ALR-N9 recorded this as waiting for BE-08 or INT-02.
- **Issue:** Every policy that reads a patient-bound alert (`staff_alert_target_select`, `_creator_select`, `_target_acknowledge`, `staff_alert_staff_insert`, the event policies) calls the stub. With it, the doctor targeted by a red flag cannot list, stream or acknowledge it, and the nurse's own INSERT is refused. The tests pass because their harness replaces the function, which hides the defect from the suites that guard it. Direction of failure is safe for data, unsafe for patients: BR-10 requires that a person is told.
- **Failure scenario:** On an integrated database a triage nurse flags chest pain. The alert row is written by the triage transaction only if the INSERT policy passes; where it does (system scope) the target never sees it and the escalation timer re-targets to someone who also cannot see it. Nothing reports the failure.
- **Remediation:** Replace the body (one `CREATE OR REPLACE`, no policy change) with the same predicate the patient policies use: realm `google`, `EXISTS (patient.staff_scope s WHERE s.patient_id = patient AND s.location_id = ANY (app.location_ids))` or the patient is in `app.btg_patient_ids`. Add a catalogue check that fails when the function body is the literal `false`, and a dbtest on the **unmodified** migrations (no testkit replacement) showing that a targeted in-scope doctor sees and acknowledges a red flag and an out-of-scope doctor does not.
- **Owner / parent:** Backend Engineer (patient or notifications lane), Integrator; QA for the unmodified-schema test. Parent HEAAA-25. Blocks RA-R1-11 acceptance and the red-flag journey.

### SEC05-F05 · Medium · The BTG flow does not exist end to end, and a grant cannot be ended
- **Where:** `grep` finds no caller of `openBtg` or `reviewBtg` outside tests in the integrated tip. The contract has `POST /patients/{patientId}/break-glass` (`audit.yaml:534`, permission `audit.btg.open`) and the staff UI calls it (`apps/staff/.../api.ts:153`, `Chart.tsx:112`); no controller implements it. BE-24's `GET /admin/btg-grants` and `POST .../review` are on branch HEAAA-120 only; they are unmounted there too (N-BE24-2) and the branch is not merged with BE-20 (migration versions 1600-1603 clash, N-BE24-6). `audit.btg_grant.revoked_at` has a column grant and a trigger rule, but no code path sets it. AUD-N5 (no FK on `btg_grant.patient_id`) is still open: no migration after 0202 adds it.
- **Issue:** The BTG dialog in the doctor portal posts to a route that does not exist. A "not justified" review leaves the grant active until it expires, because `reviewBtg` only sets `review_status`. A grant can be opened for an ID that is not a patient.
- **Failure scenario:** Clinicians who need emergency access get an error and use a workaround outside the system (shared screen, someone with access reads it out), which has no audit and no alert. Or, once the route is added, a grant judged not justified keeps working for up to 4 h (default) and the holder keeps reading.
- **Remediation:** Implement the open route as a thin wrapper over `openBtg` (permission `audit.btg.open`, `Idempotency-Key`, reason 10 to 500, **no client-supplied duration**), merge and mount BE-24 (renumber per N-BE24-6), add a revoke on `not_justified` review and a compliance "end access now" action (sets `revoked_at`, audited), and add the patient FK. QA: TC-AU-01 BTG rows and TC-SEC-20 step 3.
- **Owner / parent:** Backend Engineer (audit and clinical lanes), Integrator. Parent HEAAA-25. Blocks the BTG evidence for RA-R1-12.

### SEC05-F06 · Medium · The database does not bound a BTG grant; the review UPDATE path skips the reviewer check; duration comes from the caller
- **Where:** `0203` `btg_grant_open` WITH CHECK pins holder, person, realm, `pending`, `revoked_at IS NULL` but not `opened_at`, `expires_at` or `reason`, and `GRANT SELECT, INSERT ON audit.btg_grant TO app_api` covers every column. `0203` `btg_grant_review` (UPDATE) has no `holder_person_id <> app.person_id` condition and does not require a `btg_review` row. `service.ts:129` accepts `durationSeconds` from the caller up to 24 h; ARCHITECTURE 22.2 makes the duration a **Setting** (`btg_duration`, proposed 4 h). Nothing limits how many grants one holder may stack, or ages a `pending` review.
- **Issue:** Defence in depth is missing where the architecture relies on it for the highest-risk access (insider snooping, threat 05). A bug or injection in any `app_api` handler under a staff session can insert a grant with `expires_at` in the year 2100 and `opened_at` in the past. A compliance holder with their own grant can set `review_status = 'justified'` by a direct UPDATE; only the `btg_review` insert has the reviewer rule.
- **Remediation:** Trigger or CHECK: `expires_at <= opened_at + <max setting>` and `opened_at` within a few seconds of `now()`; make `opened_at` and `expires_at` server-assigned (drop them from the INSERT column grant, default in the table); read the duration from the setting in `openBtg` and drop `durationSeconds`; in the UPDATE policy require `holder_person_id <> app.person_id` and in the guard trigger require an existing `btg_review` row for `justified|not_justified`; add a per-holder open-grant cap with an alert above it; report `pending` older than N days in the compliance queue.
- **Owner / parent:** Backend Engineer (audit lane); Architect for the setting and cap values. Parent HEAAA-25.

### SEC05-F07 · Medium · A stream's permission and scope are fixed at connect; the 60 s check covers only the session row
- **Where:** `stream/controller.ts` passes `c.scope` from the request that opened the stream; `hub.ts` `deliver` reads every later alert under `first.who.scope`; `revalidate` selects only `revoked_at`, `idle_expires_at`, `absolute_expires_at` of `identity.session`.
- **Issue:** ARCHITECTURE 32.2 states the 60 s bound for revoked or expired sessions, and that is met. It does not cover a principal whose **role, permission, location assignment or BTG grant changed** while connected. Every normal request rebuilds the scope, the stream does not. The stream keeps evaluating RLS with the old `location_ids` and `btg_patient_ids`, and `notifications.alert.read` is not re-checked.
- **Failure scenario:** A nurse is moved from location A to B, or a doctor's BTG grant expires, or the role carrying `notifications.alert.read` is removed (TC-SEC-14 shape). The open tab keeps receiving `alert` events (type, severity, alert ID, link) for patients of the old scope until the session ends (up to the absolute limit). No PHI is in the event (ST-2 holds), but the existence and timing of a red flag for a patient the user can no longer access is disclosed, and a removed role keeps a live channel.
- **Remediation:** At each 60 s revalidation rebuild the scope with the same builder as a request and close the stream (`event: closed`, client reconnects and is re-authorised) when the permission is gone or the scope changed; also close on the role-change and location-change notifications that already revoke elevation. Test: change location, remove role, expire BTG with a stream open and assert closure within the bound. If the Architect prefers to accept the gap, record it against ST-1 with the 60 s argument extended.
- **Owner / parent:** Backend Engineer (notifications lane); Architect if the gap is accepted. Parent HEAAA-25.

### SEC05-F08 · Medium · Alert target resolution is never checked for effect: recipients may be inactive, wrong realm, or unable to see the alert
- **Where:** `service.ts` `resolveTargets` (`principal` kind accepts any UUIDs, only the shape is checked); `frontdoor/adapters.ts` `onDuty` (the active-principal join is skipped for system scope; no realm check on the roster principal) and `permissionHoldersAt` (active, realm `google`, role not revoked; no role validity window); `triage.ts` (`RedFlagNoRecipientError` only when the list is empty); the insert policy has no target condition.
- **Issue:** Nothing confirms that a target is an active staff principal who passes T-STAFF for the patient, or that at least one can receive the alert. A rostered principal who is disabled, in the wrong realm, or outside the patient's location scope is a silent dead end; the alert is `open`, the timer runs, and the escalation re-targets by the same unchecked method. Admin-realm targets require the realm fix of F03.
- **Failure scenario:** The on-duty doctor on the roster was killed by the kill switch or has no scope for the patient's location. The red flag is addressed to them only; no one sees it; the nurse believes it was sent (the API returns `alertId` and `escalatesAt`).
- **Remediation:** At raise and at each escalation, intersect the resolved principals with the active principals that satisfy the same visibility predicate as the read policy (a SQL function `notifications.alert_visible_to(principal, patient)` used by both); if the intersection is empty, fall back to the location's permission holders and, failing that, raise the roster-gap alert and refuse with a clear error rather than store an unreachable alert. Test: disabled, wrong realm, and out-of-scope targets each yield no silent dead end.
- **Owner / parent:** Backend Engineer (notifications and clinical front-door lanes). Parent HEAAA-25.

### SEC05-F09 · Medium · No export rate limit or alert; the export worker does not re-check its requester
- **Where:** `audit/service.ts` `requestExport` (size check only); BE-24 `createExport` (elevation by the guard; only the global request limiter `rate-limit.ts`); `worker/.../export.ts` (no check of the requester's session, elevation or permission across chunks; SR-BE01-04); BE-24 S1 (status readable by any `audit.export.create` holder, shows filter and reason).
- **Issue:** ARCHITECTURE C5 and TC-SEC-20 step 4 require "export rate limit enforced and alerted". Each export is capped at the row limit, but the number of exports per person per hour is not, and an export raises no compliance alert. A queued export keeps running after its requester is killed or de-elevated.
- **Failure scenario:** A compromised elevated compliance account queues many exports of the full audit history (about 1M rows each, setting-dependent); download needs the same session, so it is stopped by the kill switch, but the data is assembled and the objects exist for 72 h in the sink.
- **Remediation:** Count the requester's exports in a sliding window inside `requestExport` (setting, default low) and refuse with 429 `audit.export_rate_limited`, audited as a denial, plus a compliance alert above a lower threshold (uses F03's producer); in chunk step 1 refuse and mark `failed` when the requester's principal is disabled or has no live elevation; limit status to the requester or a second permission (BE-24 S1).
- **Owner / parent:** Backend Engineer (audit lane). Parent HEAAA-25.

### SEC05-F10 · Medium · Alert-setting changes (red-flag escalation timers) are weakly audited and have no approval
- **Where:** `alerts/settings.ts` `put` audits `config_change` with only `alertType` and `escalateAfterMin` (no location, duty, previous value); the policy `staff_alert_setting_admin_delete` lets any admin-realm session delete rows, and no service method or audit exists for delete; the admin routes are not built (ALR-N12) and the DB policy requires realm `admin_pool` but not an elevation grant; `escalate_after_min` accepts 1 to 10080 minutes.
- **Issue:** ARCHITECTURE C5 requires configuration changes to be audited with who, what, before and after; the red-flag timer is a clinical safety value (D-12a). A single admin can set it to seven days, or delete the row (no timer at all, since there is no default), with no before/after record and no second person.
- **Remediation:** Route (when built) must be elevation-gated; audit `before` and `after` including location and duty; remove the DELETE grant and policy or route it through an audited method; raise a `privileged_change` alert (F03 producer) and treat a red-flag timer change as a C4-style dual-approved change or at least require a bounded maximum with an Architect-recorded value.
- **Owner / parent:** Backend Engineer (notifications lane); Architect for the maximum and approval rule. Parent HEAAA-25.

### SEC05-F11 · Medium · Anchor verification runs the whole chain in one 60 s transaction and has no failure signal
- **Where:** `verify.ts` reads every anchor and recomputes every range inside a single `withScope`; `app_worker` has `transaction_timeout = 60s`; `audit.verify_anchors` has `maxAttempts: 3`; the audit task logs a mismatch but a failed or dead job raises nothing; detection latency is up to 24 h (daily 03:10 UTC).
- **Issue:** BR-BE01-02 correctly made the default a full recompute so old tampering is found. That is fine for a few thousand events and fails once the history exceeds what one minute reads, after which the job times out three times and dies. The detective control then stops working, silently (the only trace is a dead job in the operations view).
- **Remediation:** Chunk by anchor: one job per batch of N anchors with a stored cursor and a rolling full-chain pass over a day or week; publish `audit.verify_failed` (and alert, F03 producer) when the job dies or when the last complete pass is older than a set age; also run a cheap tail check (last day) hourly so detection latency is not 24 h. Test: a history large enough to exceed the bound still completes across chunks.
- **Owner / parent:** Backend Engineer (audit lane); DevOps for the dead-job alarm. Parent HEAAA-25.

### SEC05-F12 · Low · The denial-write failure hook is not wired, so TC-AU-03's "alerted" half has no behaviour
- **Where:** `composition.ts:168` `new AuditService({ logger, queue })` omits `onDenialWriteFailure`; `recordDenied` logs by class only. TC-AU-03 expects the failure "logged and alerted".
- **Issue/Remediation:** The caller still gets the denial (fail closed holds). Pass a hook that raises an operations alert (counter metric plus a staff alert) and add the test.
- **Owner / parent:** Integrator, Backend Engineer. Parent HEAAA-25.

### SEC05-F13 · Low · The audit insert policy does not bind the actor, realm or audience to the session
- **Where:** `0203` `event_insert` checks organisation and the audience set only; `GRANT INSERT ON audit.event TO app_api, app_worker` covers every column.
- **Issue:** The service sets actor, realm and audience from the scope (item 3 of section 2), but the database accepts any values from any `app_api` statement. A bug or injection can write an event attributed to another person, or an `export`/`btg_review` event that did not happen, into the evidence store.
- **Remediation:** WITH CHECK `actor_principal_id IS NOT DISTINCT FROM app.principal_id`, `actor_person_id` likewise, `realm = app.realm`, `audience = app.audience`; for `app_worker` jobs allow only `realm = 'worker'` and a non-null `job_id`. The definer-owner roles that write audit rows need their own narrower checks.
- **Owner / parent:** Backend Engineer (audit lane). Parent HEAAA-25.

### SEC05-F14 · Low · The audit viewer does not record what was searched, and free-text fields can carry PHI
- **Where:** `searchEvents` writes one `view` row and deliberately omits the filter ("terms are not stored"); BTG `reason`, `user_agent` and `change` are free text shown by the viewer, BTG list and export.
- **Issue:** Threat 05 treats compliance staff as insiders too; without the filter recorded, a compliance officer's look-up of one patient or one colleague cannot be reviewed later. A clinician writing a BTG reason may type clinical detail, which the viewer and export then expose to admin sessions limited to "no PHI by default" (TC-AU-06).
- **Remediation:** Store the filter (IDs, action, resource type, time range) in `change` of the `view` row. Add a UI hint and a server-side note that reasons must not contain clinical detail; consider a length and pattern screen on `reason` (best effort), and keep `reason` out of default viewer output unless the BTG list view is open.
- **Owner / parent:** Backend Engineer (audit lane); PM for the wording. Parent HEAAA-25.

### SEC05-F15 · Low · Alert reads disclose patient and resource IDs without an audit row; a target can pre-insert its own events
- **Where:** `alerts/service.ts` `list`, `view`, `replay` return `patientId`, `resourceType`, `resourceId` and write no audit row (the architecture says the detail is read through audited routes); `1201` `staff_alert_event_staff_insert` lets a target insert `acknowledged` and `closed` events without a matching state change, and the partial unique index then makes the genuine event fail.
- **Remediation:** Record one `view` audit event per list page that contains patient IDs (count, no IDs), or document the accepted exception; require `kind` to match the alert's current status in the event policy.
- **Owner / parent:** Backend Engineer (notifications lane). Parent HEAAA-25.

## Database (migrations 1500-1502)

- `telehealth.video_session`, `participant`, `join_token`, `location_confirmation`, all `FORCE` RLS, role-targeted policies, nothing to PUBLIC. T-PAT-APPT (own rows), T-STAFF, T-SYS as in 22.10; the host (the clinician of the session) is the only staff writer.
- Triggers (PS001): a session belongs to a video reservation of the same patient and clinician; a finished session, its participants and its tokens accept no change for any role; transitions are `scheduled -> open -> ended|failed`, `waiting -> admitted|removed`, `issued -> used|revoked`; a token exists only for an admitted participant of a live session with a room; a session cannot end while it holds a live token; `location_confirmation` is insert-only; `telehealth.guard_open_patient` is the merge write guard (owner `patient_scope_owner`).
- CHECKs: recording cannot be on; device check shape; token life <= 15 min; one live token per participant (partial unique index).

## Departures and open notes (for Architect / Orchestrator / Security Reviewer)

- **D1. Two staff routes carry `/host`.** 29.3 puts the staff `GET .../video-session` and `POST .../join` on the patient's paths (same method and path, two realms). The route platform has one declaration per method and path, so the staff routes are `GET .../video-session/host` and `POST .../video-session/host/join`. `admit` and `end` have the catalogued paths. The host's poll must be passive (26.2, 38.2 item 14): `passive-routes.requested.patch` adds it to `PASSIVE_ROUTES` (outside this ticket's paths). **Needs a decision**: either the platform guard accepts one declaration per realm for a path (then these two move to the catalogued paths), or the catalogue changes. Until then `routes.test.ts` pins the current state.
- **D2. `telehealth.join_token` is new.** 22.10 says join tokens are not stored, and the vendor's token is not. The table is the record of the issue (that is what makes single use and short life enforceable, what the kill switch revokes, what the merge re-points; the ticket names "session and join-token tables").
- **D3. "Too early" uses `telehealth.not_admitted`** (409, retryable) with an `errors` entry `{path: '/joinOpensAt', code: <ISO time>}`. Section 30 has no separate code and a new one needs the Architect and `packages/contracts`.
- **D4. `join` and `location` do not store a response for replay.** A stored join response would persist a bearer credential; a location answer is already a row per attempt. The `Idempotency-Key` header is still required (400 without). `admit` and `end` use the stored-response idempotency.
- **D5. The API calls the video vendor directly only to issue a join token; closing a meeting is a worker job behind the gateway** (decision DL-1 rev 2, HEAAA-738, superseding the earlier "through the gateway" wording for the join only). ARCHITECTURE 35.2 allows the join token as a request-path vendor call. `app_api` has no write right (INSERT/UPDATE) on `outbound_call` (BE-02), and a join is not retried by a job (34.1: 503, the caller retries). The production port is `platform/aws/chime-video.ts`. It makes only `CreateAttendee`, with 3 s connect / 8 s request timeouts and at most 2 attempts, and writes one structured `vendor_call` log line per call (ids and outcome only; the token is never logged, stored or put in an error). The durable record of each issue is `telehealth.join_token`. Meeting creation (`telehealth.create_meeting`) and meeting close (`telehealth.close_meeting`, enqueued in the transaction that ends the session, by the host's `end` or by `end_stale`) run in the worker behind `VendorGateway`, which keeps the `outbound_call` log, retries, the circuit and the `video` connection health. A meeting must close reliably because Chime tokens already issued stay usable until it does. The dbtest kit runs the port over the gateway to test the worker's adapter, not as the production wiring. Reverting the join to a gateway-backed port is a composition-root change.
- **D6. Kill switch (ST-4).** The kill switch should revoke a principal's live join tokens in its own transaction (BE-05 lists them). The tokens' policies cover the patient, the host and the worker, not the admin-realm kill-switch transaction, and identity is outside this ticket. Not delivered; the bound is the 15-minute token life. Needs a decision (a definer function owned here, or a policy for the identity role).
- **D7. M-5 definer inventory.** `telehealth.guard_open_patient` needs one line in `db/tools/catalog-lists.mjs`: `catalog-lists.requested.patch` (outside this ticket's paths, as for BE-02/BE-13). **Do not integrate before the F-03 owner applies it**: the catalog check is red on this ticket's function without it.
- **D8. Vendor events are not handled.** `used` (token) and `left_at` from the vendor's participant events, and the "event after the session ended is recorded handled with no change" rule, need the chosen vendor's event shapes (C-11). The status `used` exists and is never set until then; sessions are closed by the host, the stale job or the 15-minute token life.
- **D9. The session row is made when the booking is confirmed**, not at start - 15 minutes (33.1 says only the meeting is created ahead of time): a device check needs the row. The room is still made at start - 15 minutes.
- **D10. `participant.admission = 'removed'`** has a state and a trigger but no route (29.3 has none); a "let back in" is `removed -> admitted`.
- **D11. The window is a constant** (10 minutes before the start; TC-TH-05), not a setting; no setting is listed in 31.4. A setting is a one-line change in `rules.ts` and the Architect's list.
- **D12. `patient_stated_state` at booking vs. the answer at join.** The booking stores the state the patient gave; the join re-asks (RA-R1-28) and keeps every answer. The licensed states are read from `identity.licensed_state` exactly as BE-11 does (an expired licence does not count).
- **D13. Real states.** All state values in tests are placeholders (NY allowed and licensed, CA allowed but not licensed, NJ not an operating state). Production values wait for D-2.

## What it does

| Interface (ARCHITECTURE 24) / route          | Where                                                   | Behaviour                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| -------------------------------------------- | ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `status` `GET /calendar-link`                | API `service.ts`, `controller.ts`                       | The doctor's own link: status, calendar, `lastSyncedAt`, `lastErrorCode`. Never a token, sync token or secret name.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `linkStart` `POST /calendar-link/start`      | API                                                     | Creates the link `pending_consent` (once) and returns the Google consent URL: offline access, S256 PKCE, the two minimal scopes (`calendar.events`, `calendar.freebusy`). `state` and the PKCE verifier are **stateless** (HMAC, `state.ts`): no table.                                                                                                                                                                                                                                                                                                                                                                            |
| `linkComplete` `GET /calendar-link/callback` | API                                                     | Verifies the state (same principal as the session, 10 minutes, current or previous key) **before** anything is read or exchanged, exchanges the code outside any transaction, then ONE transaction: secret store `put` (idempotent token), `secret_ref` row (name + version ID), audit `secret_write` (version ID), link `active`, and the first listing (`full_resync`, marker `initial`) and the watch channel enqueued. 302 back to the portal with `?calendar=linked\|denied\|error`; never the code or the state.                                                                                                             |
| `unlink` `DELETE /calendar-link`             | API                                                     | Deletes the link, enqueues `calendar_sync.unlink_cleanup` (departure D3).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `POST /webhooks/google/calendar`             | API `push.ts` over integration-core's `InboundReceiver` | HMAC channel token verified **without reading `watch_channel`** (pure check, key from the secret store); `401` wrong or expired token, `400` unknown resource state or malformed number, nothing recorded; valid: stored under `<channel id>:<message number>` (a repeat is a duplicate: `200`, no second job) and the dispatch job enqueued in the same transaction.                                                                                                                                                                                                                                                              |
| Push handler                                 | worker `push-handler.ts`                                | Registered for source `google_calendar`. Validates the payload strictly (DF-3), matches channel **and** resource ID to an unexpired `watch_channel` row, ignores anything else, ignores the `sync` handshake, enqueues one keyed `incremental_sync`. The push is never the change source.                                                                                                                                                                                                                                                                                                                                          |
| `calendar_sync.push_busy` / `delete_busy`    | worker `push-busy.ts`, `handlers.ts`                    | A confirmed booking becomes ONE Google event titled **"Busy"** (private, opaque, no description/attendee/location, our marker only). The job reads the occupancy only (doctor, interval, status). Deterministic event ID (`ehr` + the occupancy's 32 hex digits), `event_map` state, 409 on a repeat is made equal with a PUT, 404/410 on delete is done, and a cancel that raced a push removes what the push made.                                                                                                                                                                                                               |
| `calendar_sync.incremental_sync`             | worker `sync.ts`                                        | Every 15 minutes (fan-out) and on a push. Lists with the sync token (vendor calls outside any transaction), then one transaction: lock the link, require the token is still the one the listing began from, merge the delta into the current rows and call `scheduling.replace_busy_blocks` with the **complete** set, store token and `last_synced_at`.                                                                                                                                                                                                                                                                           |
| `410 Gone` rule (QA-AL-01)                   | worker `sync.ts`                                        | S rejected: lock the link, `sync_token = NULL` only if still S, store SHA-256(S), enqueue `full_resync` (key clinician + marker); **no busy block changes**. A null token never means "wait": `incremental_sync` calls nothing at Google and enqueues the keyed resync (marker = last discarded hash, else `initial`). `full_resync` lists every page without a token, then in one transaction stops if a token appeared, else replaces the doctor's blocks with the complete set and stores the new token. A failed listing keeps the old blocks and `last_synced_at`; a dead resync is enqueued again by the next 15-minute run. |
| `calendar_sync.renew_watch`                  | worker `watch.ts`                                       | Daily sweep: a link needs a channel when none has more than 36 h left or the only one is signed with an older key version. Token `v.<key version>.<expiry>.<HMAC>` (expiry <= 7 days, = the channel expiry). New channel registered **before** the old one is stopped. No token and no token hash is stored.                                                                                                                                                                                                                                                                                                                       |
| Google adapter                               | worker `google-adapter.ts`                              | `VendorAdapter<'google_calendar'>` for integration-core's `callVendor` (log, retry, circuit are the gateway's). Fixed hostnames, no title/description/attendee/location requested, intervals only returned, errors carry no body.                                                                                                                                                                                                                                                                                                                                                                                                  |
| `scheduling.replaceBusyBlocks`               | migration `1403` (`scheduling.replace_busy_blocks`)     | `SECURITY DEFINER`, owner `scheduling_booking_owner`, `EXECUTE` to `app_worker` only, organisation-wide system job only, validated arguments (22023), per-doctor advisory lock, replace-by-set keyed by `external_hash`. No application role can write `busy_block` any other way.                                                                                                                                                                                                                                                                                                                                                 |
| Revoked grant                                | worker `sync.ts`                                        | `401`/`invalid_grant` -> link `token_revoked` (+ `last_error_code`), `calendar_sync.link_broken` published once (IDs only), no retry loop, busy blocks stay (stale warning, not a freed slot). Re-linking recovers it.                                                                                                                                                                                                                                                                                                                                                                                                             |

## Database (migrations 1400-1403)

- `calendar_sync.calendar_link`, `watch_channel`, `event_map` (22.9), all `FORCE` RLS with role-targeted policies, nothing to PUBLIC. `calendar_link`: own row for a google-realm doctor (T-PRINCIPAL), admin read (operations view), worker (T-SYS). `watch_channel`, `event_map`: worker only; **no API role has any right**. The API role cannot read `sync_token` or `discarded_token_hash` (column grants).
- Triggers: a new link starts `pending_consent`; a link cannot become `active` unless the doctor's token reference exists (PS001); identity columns are immutable; `token_secret_name` is fixed to `cal-<principal id>` by CHECK.
- `1402` also adds four narrow policies on `integration_core.connection` / `secret_ref` (departure D2).
- Class C1 only: no patient column anywhere in the schema.

## Departures and open notes (for Architect / Orchestrator / Security Reviewer)

- **D1. `scheduling.replace_busy_blocks` is created here** (the BE-12 README, D5, names BE-14 as its writer). It is a definer function, so it needs one line in the M-5 definer inventory: `catalog-lists.requested.patch` (outside this ticket's paths, as for BE-02/BE-13). With it, the catalog check no longer lists the function; the other failures it reports (`M-4-views`, `M-5-patient-guard`, `M-5-definer` for other tickets' functions, `M-5-public`, `M-5-directory`) are present on the base revision and are other tickets' requested patches. **Do not integrate before the F-03 owner applies the patch.**
- **D2. Cross-module policies on `integration_core` (`1402`).** BD-11 lets the API write an outbound secret reference, but the BE-02 policies allow it only to the admin realm, and the callback runs as the doctor. Added, additive and narrow: a google-realm doctor may SELECT the one `google_calendar` connection, and SELECT/INSERT/UPDATE exactly the `outbound` reference named `cal-<own principal id>` of that connection. Tested: another doctor's name, the inbound class, another connection kind, and the OAuth client secret are all refused. **Security Reviewer: confirm this is the intended reading of SA-DP-06 / ARCHITECTURE 22.9** (the alternative is a definer function owned by an integration owner role, which needs a role this ticket cannot create).
- **D3. Extra job `calendar_sync.unlink_cleanup`** (not in 33.1). `DELETE /calendar-link` must free the doctor's busy time and stop channels. Skipped if the doctor has linked again. Needs an Architect decision to stay.
- **D4. The timer and the push use the design's job names without a payload token.** `incremental_sync` is "clinician + sync token" in 33.1, but a token is not an ID (BD-09 refuses it in a payload), so the job carries the clinician and reads the token from the link. With no clinician it is the 15-minute fan-out; `renew_watch` without a clinician is the daily sweep. Cron cannot carry a per-doctor payload, so the overload is the smallest change; a separate sweep job type is the alternative.
- **D5. `calendar_link.discarded_token_hash`** (not in 22.9): the resync marker "SHA-256 of the last discarded token" needs somewhere to live. The hash only; markers travel as the first 128 bits formatted as a UUID because the queue's IDs-only rule refuses a 64-character hex string.
- **D6. Refresh tokens: store write by the API, read by the worker.** `OutboundSecretStore.put` is BE-02's interface; the value goes in `put` and nowhere else. The reference name is `cal-<principal id>` (the store path `<env>/integration/outbound/calendar/<principal id>` of 22.9 is the store implementation's choice from connection ID + name).
- **D7. The OAuth client secret is read by the API.** The code exchange needs it, and 9.1 makes outbound secrets write-only for the API. `GoogleCalendarOAuth` takes it as an application secret of the API task (like `qr_key`); the worker reads `oauth-client-secret` through `secret_ref` for refreshes. **Architect/Security: confirm.**
- **D8. Freshness of an empty calendar (BE-12 D4).** `calendar_link.last_synced_at` now exists but slot search still derives freshness from `busy_block.synced_at`, so a linked doctor with no busy blocks is never flagged stale. Changing `search.ts` is BE-12's (outside this ticket's paths).
- **D9. Window of a listing.** A full listing covers [now - 1 day, now + 400 days]; a sync token covers the same set. An event created beyond the horizon reaches us only at the next full listing (a `410`, a re-link). Google may also expire a token itself. A periodic forced resync is not specified; not added.
- **D10. Route wiring.** `calendarResolvers()` registers the resolver name `calendar-own` (the contract says `own`). The webhook route is declared here and needs the integrations host wiring of BE-22; verification keys are `inbound_verification` secrets: the channel key is read through `InboundKeyProvider.keys('google_calendar')`, which the deployment maps to `<env>/integration/inbound/google-calendar-channel-key` (current + previous). Raw-body capture is not needed (no body).
- **D11. TC-CAL-07..16 do not exist.** The ticket cites `TC-CAL-01..16`; the frozen TEST-CASES define `TC-CAL-01..06` only.
- **D12. Resource IDs.** BE-02's push verifier accepts a `X-Goog-Resource-ID` up to 256 characters, the table and handler 255; a 256-character one is stored and then ignored (Google's are ~20 characters).
- **D13. No revoke at Google on unlink.** The adapter contract has no `revoke` operation (a contract change). The stored version stays in the secret store until its lifecycle ends; re-linking overwrites it.
- **Unverified (C-10).** Everything that talks to Google is proven against a local contract stub: request shapes, the `fields` mask, 401/403/409/410 handling, token refresh. The documented behaviours the stub assumes (event `id` rules and 409, `syncToken` with `singleEvents`/`showDeleted`, channel `expiration`, the two scopes) are unverified against the real service; real-Google evidence (TC-CAL-01..06 on `ENV-INT/staging`) is BLOCKED until the test tenant exists.

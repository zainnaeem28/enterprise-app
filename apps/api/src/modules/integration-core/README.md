# integration-core module (BE-02)

Owner: Backend Engineer. Migrations `0400`-`0402`, API side here, worker side in `apps/worker/src/jobs/integration-core`.
Design: ARCHITECTURE 22.3, 24, 25.7, 25.9, 33.1, 34; SHARED-BOUNDARIES 3.2 rule 6, 9.1 (BD-11); SEC-01 (DF-1..4, SC-1..8, O2-1..9).

## What it does

| Interface (ARCHITECTURE 24)                       | Where                   | Behaviour                                                                                                                                                                                                                                                                                                     |
| ------------------------------------------------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `callVendor(kind, op, args, correlation)`         | worker `call-vendor.ts` | Loads the connection (enabled), asks the circuit, calls the adapter under a timeout, retries retryable failures with exponential back-off + jitter, **logs every attempt** (including refusals) in `integration_core.outbound_call`. A vendor without an idempotency token gets a `pending` row first (34.3). |
| Adapter interface per kind                        | worker `adapters.ts`    | `email`, `sms`, `push`, `video`, `google_calendar`, `ocr`: operation lists, `call`, `healthCheck`, optional `find` (lookup by correlation ID). Concrete adapters arrive with the tickets that need them.                                                                                                      |
| Circuit state                                     | worker `circuit.ts`     | Per connection in memory: open after 5 consecutive failures or 50 % over 20 calls in 1 min; half-open after 30 s with one probe. A vendor 4xx does not count.                                                                                                                                                 |
| `registerInboundHandler(source, type, handler)`   | worker `dispatch.ts`    | `InboundHandlerRegistry.register`; one handler per pair.                                                                                                                                                                                                                                                      |
| `readInbound(messageId)`                          | worker `dispatch.ts`    | Reads and decrypts a stored message (context = source + event ID).                                                                                                                                                                                                                                            |
| `integration_core.dispatch_inbound`               | worker `dispatch.ts`    | Runs the handler; no handler -> `no_handler` (dead-letter view); handler error -> `failed` + job failure (8 attempts).                                                                                                                                                                                        |
| `connectionSettings(kind)` and admin upsert       | API `connections.ts`    | Non-secret settings, health, last test; changes audited with before/after.                                                                                                                                                                                                                                    |
| Webhook transaction                               | API `inbound.ts`        | verify (no table read) -> seal -> **one transaction**: `receive_inbound`; if `inserted`, `queue_api.enqueue` of the dispatch job and the `inbound_received` event. Duplicate: 200, nothing enqueued. Failure: 503, nothing stored.                                                                            |
| Webhook rules                                     | API `verifiers.ts`      | Generic `HMAC(ts.body)` with a 5-minute window; Google Calendar channel token (29.5). Vendor-specific schemes are added with their adapters.                                                                                                                                                                  |
| Outbound secret write                             | API `secret-service.ts` | Value -> store (idempotent token), reference + audit (`secret_write`, version ID) in one transaction. Never returns, logs or audits the value.                                                                                                                                                                |
| Inbound-verification secret (dual control)        | API `secret-service.ts` | `requestInboundSecret` -> a different admin `decide`s -> the **worker** applies after re-checking the evidence (`apply-secret.ts`).                                                                                                                                                                           |
| `integration_core.health_check` (every 5 minutes) | worker `health.ts`      | Probes every enabled connection, writes `connection.health`; a change into `down` publishes `connection_down`, out of `down` `connection_restored`, in the same transaction.                                                                                                                                  |

## Database rules (migrations 0400-0402)

- Five tables, all FORCE RLS, role-targeted policies, nothing to PUBLIC: `connection`, `secret_ref`, `secret_change_request`, `outbound_call` (monthly partitions Nov 2026 .. Dec 2027 + default), `inbound_message`.
- JSON columns refuse credential-looking keys (`has_secret_like_key` CHECK). `secret_ref.secret_arn` must sit under `/integration/outbound/` for class `outbound` and `/integration/inbound/` for `inbound_verification`.
- BD-11 write split by policy: `app_api` (admin realm) writes only `outbound` references; `app_worker` only `inbound_verification`.
- `secret_change_request`: approver <> requester by CHECK, RLS and trigger; identity columns, hash and expiry immutable; forward-only status; no delete.
- `outbound_call`: no delete; a `pending` row moves once to its outcome; the worker's UPDATE is column-limited.
- `receive_inbound`: `SECURITY DEFINER`, owner `integration_receiver_owner`, `search_path = pg_catalog`, `EXECUTE` to `app_api` only, refuses any audience except none/`anonymous`, validates every argument (22023). `app_api` has no right on `inbound_message`.

## Deviations and open notes (for Architect / Orchestrator / Security)

- **INT-N1 anonymous policy.** ARCHITECTURE 21.3's "complete" anonymous list does not include `inbound_message_receive`, but 25.7 needs an insert with no session. The policy is `TO integration_receiver_owner` only and also requires audience none/`anonymous`. M-5 (`anonymous`) lists it, and the M-5 definer inventory must list `receive_inbound`. Both are in `catalog-lists.requested.patch` (outside this ticket's paths, like BE-03's patch). **Do not integrate before the F-03 owner applies it**: the repo catalog check is red on this ticket's objects without it (verified green with it: 18/18). The kernel setter has no "no audience" value, so the webhook transaction uses `anonymous`.
- **INT-N2 no HTTP routes.** The three webhook routes and the admin routes of the catalogue need the platform layer to keep the **raw request bytes** (signatures cover them; `app.useBodyParser('json')` consumes them) and the identity guard policy. `InboundReceiver.receive` takes the raw bytes and returns the status to send; the controller is an integration step. TC-API webhook parts are run at this service boundary against the real database, not over HTTP.
- **INT-N3 canonical bytes omit the approver.** O2-1 lists the approver's person ID, but it is unknown when the request is created and the stored bytes are immutable. The worker binds the approver instead (credential owner = approver person <> requester). Security Reviewer to confirm.
- **INT-N4 sealed payload transport.** 25.9 / BD-09 allow one exception: the sealed value travels as the apply job's payload. The kernel queue (`assertPayloadIsIdsOnly`, and `queue_api.enqueue`'s string gate) refuses it, and kernel is outside this ticket. `SecretService` takes an injected `enqueueApply`; without it a request fails closed (503) and nothing is stored. The worker task accepts `{requestId, sealed}` and re-enqueues itself every 30 s until the request is approved, expired or rejected. **Needs a kernel/F-04 amendment before inbound-secret entry works end to end.** SC-5 (null the queue payload at a terminal state) is part of that amendment.
- **INT-N5 evidence verifier.** O2-3/O2-4 (two WebAuthn assertions, anchored and aged credentials) need identity (BE-04/BE-05). The worker takes an `ApprovalEvidenceVerifier`; the default **refuses everything** (`no_verifier_configured`), so no admin-entered inbound secret can be applied until identity supplies one. The refusal closes the request, audits the reason class and publishes `integration_core.secret_change_refused` (compliance alert). TC-AD-14 is proven with the default and with a permissive fake that shows the worker passes the recomputed challenge.
- **INT-N6 `pending` outcome.** 22.3 lists `ok/timeout/error/rejected`; 34.3 needs `pending`. Added to the CHECK, with a guard so a row moves once. Also added: `error_class`, `health_changed_at`, applied-version columns, assertion columns (SEC-01 section 5). `rejected` means "refused before it left" (circuit open, disabled, no adapter).
- **INT-N7 vendor hostnames.** SEC01-F-12: hostnames come from code or IaC, never from `settings`; the concrete adapters (not in this ticket) must enforce a per-vendor allowlist.
- **INT-N8 secret store, KMS, SES/SMS vendors** are interfaces here (`OutboundSecretStore`, `InboundSecretWriter`, `PayloadSealer`, `PayloadOpener`, `InboundKeyProvider`); the real implementations belong to DevOps/infrastructure tickets. No cloud call was made.
- **INT-N9 crontab.** `INTEGRATION_CORE_CRONTAB` is not passed by the F-05 runner yet (same as `AUDIT_CRONTAB`); jobs are registered in `JobRegistry`, and `queue_api.task_type` is synced by `syncTaskTypes`.
- **INT-N10 operations alerts.** The events are published; the `notifications` handlers (alert rows) belong to the notifications ticket. The dead-letter and operations views are `reporting` (`reporting.refresh_ops`).

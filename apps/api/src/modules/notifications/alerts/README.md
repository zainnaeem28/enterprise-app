# staff alerts and the alert stream (BE-07)

Owner: Backend Engineer. Migrations `1200`-`1201`. Code: `alerts/` (service, escalation logic, settings, routes, merge contribution) and `stream/` (hub, event
serialiser, stream controller), both under the notifications module.
Design: ARCHITECTURE 5.4, 22.13, 25.5, 29.3, 30, 32, 33.1, 38.2 items 6 and 19; ADR-009, ADR-022; PRD BR-10 (mechanics only); TC-PC-16, TC-SAF-01/02/04.

## What it does

| Interface                                            | Where                                                     | Behaviour                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ---------------------------------------------------- | --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `raiseAlert(type, targets, resourceRef, patientId?)` | `AlertService.raise`                                      | One transaction: the alert row, its `created` event, and (when an escalation time exists) the `notifications.escalate_alert` job at `escalate_at`. Targets (`principal`, `role_location`, `compliance_permission`) are resolved to principals **now** through the injected `TargetResolver`, de-duplicated; no principal means refusal, never an alert nobody can see. An admin-realm type with a patient ID is refused in the service **and** by a CHECK. The trigger `staff_alert_notify_*` runs `pg_notify('staff_alert', ...)` in the same transaction: a rolled-back alert notifies nobody, a committed one always does.                                               |
| `escalate(alertId, targets)`                         | `AlertService.addEscalationTargets`                       | T-SYS only. Resolves again (ADR-022), **adds** principals (the table refuses removal), re-notifies. Closed alerts refuse (`409`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `notifications.escalate_alert`                       | `escalateAlert` (`escalate.ts`), declared in `ALERT_JOBS` | Row-locked re-read; does nothing for closed, acknowledged, already escalated, no timer, stale level; runs early -> puts the same job back (`rescheduled`); otherwise level 1, `status = escalated`, `escalate_at = NULL`, one `escalated` event, publishes `notifications.alert_unacknowledged`. Idempotent by (alert, level): the event table allows one `escalated` per alert.                                                                                                                                                                                                                                                                                            |
| `GET /alerts`, `GET /alerts/open-ids`                | `createAlertsController`                                  | Own targets only (RLS **and** an explicit `principal = ANY(targets)`; a red flag's creator can read the row in her own transaction but never sees it in a tray). `status=open` = `open` + `escalated` (N-6). `escalatesAt` is non-null only while `open` with a timer. `acknowledgedByDisplayName` from `identity.staff_profile`.                                                                                                                                                                                                                                                                                                                                           |
| `POST /alerts/{id}/acknowledge`                      | same                                                      | Idempotency-Key. `SELECT ... FOR UPDATE`, so two simultaneous targets run one after the other: both 200, one has `alreadyAcknowledged: true`, exactly one `acknowledged` event (also a partial unique index). Closed: `409 notifications.alert_closed`. Not a target: `404`.                                                                                                                                                                                                                                                                                                                                                                                                |
| `GET /alerts/stream`                                 | `StreamHub` + `createAlertStreamController`               | Replay of the caller's open/escalated alerts with `seq > Last-Event-ID` in `seq` order (`resync` instead when more than 200); live events from one dedicated `LISTEN` connection (reconnect with back-off, then a catch-up replay); every notification is turned into events by **re-reading under each local target's own scope**; 15 s ping; 60 s per-stream session re-read (spread by a random offset) closes revoked/expired streams; `session_revoked` closes at once; 3 per session / 10 per principal (oldest closed); 64 KB write buffer, a slow client is destroyed, never buffered; `closed` on drain. Events carry only the closed field list (`serialize.ts`). |
| Settings                                             | `AlertSettingService`                                     | `staff_alert_setting` (type, location, minutes, duty). The `/admin/alert-settings` routes are thin wrappers (admin realm, elevation) left to integration.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Merge / export                                       | `repointAlertRows`, `alertExportContributor`              | R: open/acknowledged/escalated re-point; K: closed and all events.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

`escalatesAt` source: `staff_alert_setting` (location row, then organisation row); for `red_flag` the clinical setting `red_flag_escalation_minutes` is the fallback.
**There is no default for `red_flag` anywhere** (D-12a): no value means `escalatesAt = null` and no job.

## Open notes

- **ALR-N1 two sources for the escalation time.** ARCHITECTURE 25.5 says `staff_alert_setting`; 38.2 item 19 and the setting catalogue name `red_flag_escalation_minutes`. Both are read (table first). Architect to pick one; either way there is no default.
- **ALR-N2 the worker handler is not written here.** `apps/worker/src/jobs/notifications` is outside this ticket's paths. `escalateAlert(tx, queue, {alertId, level}, {jobId, audit})` is the whole logic: the worker handler opens a patients-scope transaction when the payload carries `patientId`, an org-scope one otherwise, and calls it. The job type (`ALERT_JOBS`) must be added to `NOTIFICATIONS_JOBS` or the worker registry (a test compares the lists in BE-06). **Request to the Orchestrator.**
- **ALR-N3 the platform's transport-only stream controller owns `GET /alerts/stream`** (`apps/api/src/platform/stream.ts`, F-05). Two controllers cannot own a route, so integration replaces it with `createAlertStreamController(hub, identityOf)` and starts `hub.start()` / `hub.stop()` with the app. The tests mount ours in the real platform stack (release middleware, identity guard, filter) without `createApp`. Also needed: `drain()` from the lifecycle hook. **Request to the Orchestrator.**
- **ALR-N4 merge participant.** `notifications/merge.ts` has the single participant; it must add `ALERT_MERGE_TABLES`, `ALERT_CONFLICT_RULES` and call `repointAlertRows` / `alertExportContributor` (NOT-N12). Outside this ticket's paths. **Request to the Orchestrator.**
- **ALR-N5 resolved by HEAAA-286 (draft 8.3):** `doctor` holds `notifications.alert.read` and `.acknowledge` (and `trainee_doctor` inherits them).
- **ALR-N6 realms.** 32.2 point 1 accepts `google` **and** `admin_pool` on the stream; `RouteDeclaration.realm` takes one value and the guard defaults a non-`/admin` path to `google`. An `admin_pool` compliance session is therefore refused (403) on `/alerts*` today. The service and RLS support it (tested at service level). Needs a platform/guard change (a realm list on the declaration). **Request to the Orchestrator.**
- **ALR-N7 `catalog-lists.requested.patch`.** M-5 flags `notifications.staff_alert` and `staff_alert_event` until `patient.guard_open_patient` exists (same as NOT-N4). The patch adds both to `interimGuardExempt` (BE-08 removes them). With it, `db/tools/db-test.mjs` passes 29/29; without it, M-5 fails (and the organisation dbtest that runs the same check). `db/tools` is outside this ticket's paths.
- **ALR-N8 lint exemption.** `alerts.dbtest.ts` imports the BE-04 `testkit` (the only real-stack harness) and disables `boundaries/module-boundaries` for that one import. A rule exemption for `testkit` in `*.dbtest.ts` would remove it.
- **ALR-N9 T-STAFF fails closed.** `notifications.staff_scope_allows_patient(patient)` returns `false` until BE-08 (`patient.staff_scope`). A staff session sees and creates **only** alerts without a patient; a `red_flag` is invisible to staff, and a staff transaction cannot insert it. BE-08 or INT-02 replaces the body of that one function. The tests prove the closed state first, then replace the function in the test database with a stand-in (`patient = P1`) to exercise the rest. **Staff-created red flags (the triage transaction) cannot be demonstrated end to end until then.**
- **ALR-N10 `seq` and commit order.** `seq` is assigned at insert; commit order can differ, so a reconnect with `Last-Event-ID` could skip a lower `seq` committed later. The 60 s `open-ids` poll (32.2 point 6) repairs it; a longer-term fix is a gap check in the replay.
- **ALR-N11 link.** `link` is `/alerts/<alertId>` (IDs only). The page route belongs to the staff app; change `alertLink` if FE names another.
- **ALR-N12 admin routes.** `GET/PUT /admin/alert-settings` have opaque bodies in the contract; only the service exists here.
- **ALR-N13 SSE behind CloudFront and the ALB is Unverified** until the DevOps staging test (C-01). Nothing here proves proxy behaviour: the 15 s ping is the design's answer, tested only against a direct connection.
